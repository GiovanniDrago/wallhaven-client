# Kotlin/Android F-Droid publication

Publish a new app or update an existing native Android app in `fdroiddata`. The app must
be built with Gradle (Kotlin or Java). The skill covers the upstream repository and the
F-Droid metadata repository, delegates the two independent workstreams to subagents, and
stops at a **draft** merge request.

For Flutter apps use `flutter-fdroid-publish` instead. The build recipes are not
interchangeable.

## Modes

- `new`: `metadata/<package-id>.yml` does not exist in `fdroiddata`.
- `update`: the app already exists; replace the old build block with the new release.

Ask the user to confirm the mode. When the network is available, check:

```text
https://gitlab.com/fdroid/fdroiddata/-/raw/master/metadata/<package-id>.yml
```

## Non-negotiable rules

- Work only on a **fork** of `fdroiddata`; never push to `fdroid/fdroiddata`.
- Push only after every gate in Phase 3 passes. Never force-push.
- Open the MR as **draft**. Never mark it ready without an explicit user instruction.
- Metadata is YAML (`metadata/<package-id>.yml`). Do not create XML; the F-Droid index is
  generated by the server.
- Do not put summary, description, changelog, icon, or screenshots in the metadata. They
  belong in the upstream `fastlane/metadata/android/en-US/` tree.
- Use one full commit hash, not a tag or branch, in `Builds.commit`.
- Keep only the latest release in the metadata. Do not add disabled build blocks.
- Never invent a signing key, category, package ID, version code, APK URL, or tag.
- Do not store tokens, passwords, or keystore contents in the context file.
- One app per MR.
- Write metadata, commits, and the MR in English. Talk to the user in the user's language.

## Reproducibility contract

The default mode is reproducible:

- the release tag and APK asset name contain both the version name and the version code;
- `Builds.binary` uses `%v` and `%c` so F-Droid can reconstruct the asset URL;
- `versionCode` increases on every release;
- the Gradle build supports `-Pfdroid` and produces an unsigned release APK;
- the upstream workflow and the F-Droid recipe use the same version, SDK, and build path
  where the toolchain requires it.

If the reproducible contract cannot be met, stop and ask the user before falling back to
an unsigned F-Droid build without `binary:`. Never remove `binary:` silently.

## Phase 0 — Interview and context

Read `references/interview.md` before asking anything. Ask the questions in one batch,
with defaults, and do not start work until the user confirms.

1. Detect the local GitLab identity. Run `glab auth status` and `glab api user` when
   available; otherwise check `git config user.name` / `user.email` and ask. If exactly one
   GitLab host/account is authenticated, propose it as the default fork owner. If several
   are authenticated, list them and ask.
2. Confirm `new` or `update`, app repository, package ID, app name, version, version code,
   release tag, asset name, module/subdir, license, author, issue tracker, RFP issue, and
   whether the upstream repository may be modified and pushed.
3. Confirm the fork host, namespace, protocol, and whether the fork already exists. Check
   that the fork is public and the target branch is not protected.
4. Read `references/reproducibility.md` and confirm the reproducible tag/asset templates
   and the `fdroid` signing property.
5. Read `references/categories.md`, fetch the live category list, and propose one primary
   category plus alternatives. Wait for the user's choice.
6. Write `fdroid-context.json` from `assets/context.example.json` and validate:

   ```bash
   scripts/validate_context.py --schema assets/context.schema.json fdroid-context.json
   ```

7. Show the planned upstream edits and ask for one explicit approval. Record it in
   `approvals`.

Work directory: `<paths.workRoot>/<package-id>/` with `upstream/` and `fdroiddata/`
clones. Never reuse a dirty work tree.

## Phase 1 — Parallel subagents

Read `agents/kotlin-fdroid-repo-prep.md` and `agents/kotlin-fdroid-metadata.md`; both are
self-contained role prompts. If the companion agents were installed with
`install.sh --with-agents`, you may launch them by name. Otherwise launch `general` with
the full role prompt.

Launch both in the same turn with the `subagent` tool, `background: true`, and:

- the full role prompt (or the installed agent name);
- the absolute path to `fdroid-context.json`;
- the work directory and the handoff directory;
- the rule "do not push; commit locally only".

`kotlin-fdroid-repo-prep` writes `handoff/upstream.json` and a short report.

`kotlin-fdroid-metadata` performs its independent preparation (fork, tools, categories,
metadata skeleton, MR body), writes `handoff/publication-draft.json`, then stops.

Do not wait for one before launching the other. Keep both session IDs.

## Phase 2 — Synchronize and validate

1. Wait for `kotlin-fdroid-repo-prep`. If it failed, stop and report; do not let the
   metadata agent guess.
2. Resume `kotlin-fdroid-metadata` with the same session ID. Give it the path to
   `handoff/upstream.json` and ask it to finalize the metadata and run the validation
   matrix in `references/validation.md`.
3. Read `references/validation.md` yourself and run the independent check:

   ```bash
   scripts/validate_metadata.py \
     --context fdroid-context.json \
     --handoff handoff/upstream.json \
     --metadata fdroiddata/metadata/<package-id>.yml \
     --categories-json handoff/categories.json \
     --check-urls --check-apks --check-remote --check-diff
   ```

4. If either check reports an error, return to the metadata subagent with the exact
   output and let it fix and re-run. Cap the loop at five iterations, then stop and report
   the blockers.

## Phase 3 — Release gate

Push only if all of these are true:

- [ ] `versionCode` is greater than the previous release and the tag points to the release
      commit.
- [ ] The release tag and asset name match the reproducible templates.
- [ ] `./gradlew assembleRelease -Pfdroid` produces an unsigned APK.
- [ ] `fdroid readmeta` succeeds.
- [ ] `fdroid rewritemeta <package-id>` produces no diff.
- [ ] `fdroid lint -f <package-id>` reports no errors.
- [ ] `fdroid checkupdates --allow-dirty <package-id>` confirms the version and does not
      propose a different one.
- [ ] `scripts/validate_metadata.py` exits 0.
- [ ] The APK URL returns HTTP 200 and its SHA-256 matches `handoff/upstream.json`.
- [ ] The signing certificate SHA-256 matches `AllowedAPKSigningKeys`.
- [ ] `git status --porcelain` contains only `metadata/<package-id>.yml` in `fdroiddata`.
- [ ] The fork is public, the branch is not protected, and the commit exists upstream.
- [ ] The MR body is complete, every checked box has evidence, and no placeholder remains.
- [ ] `approvals.upstreamPush` and `approvals.autoPush` are `true`, and
      `approvals.neverReadyWithoutUser` is `true`.

Ensure both branches have local commits, then push the upstream branch/tag and the
`fdroiddata` branch:

```bash
git -C upstream push origin HEAD:<upstream-branch>
git -C upstream push origin <release-tag>
git -C fdroiddata push -u origin <package-id>
```

Open the draft MR only through the script, after the gate:

```bash
scripts/create_draft_mr.sh \
  --repo fdroid/fdroiddata \
  --head <namespace>/fdroiddata \
  --source <package-id> \
  --target master \
  --title "New app: <AppName>" \
  --body-file handoff/mr.md \
  --label "New App" \
  --execute
```

For `update`, use `--title "Update <AppName> to <version>"` and omit `--label`.

## Phase 4 — Handoff

Report:

- the MR URL and the fork branch;
- the pipeline URL and its current status;
- validation evidence and the reproducible-build result;
- remaining work: reviewer feedback, pipeline, and the user's decision to mark the MR ready.

Mark it ready only after an explicit instruction:

```bash
glab -R fdroid/fdroiddata mr update <mr-id> --ready
```

## Stop conditions

Stop and ask the user when:

- no GitLab authentication is available and the user does not want to configure it;
- `glab` is missing and the user does not want to install it; in that case push the branch,
  print the MR creation URL, and stop before the draft MR step;
- the fork is private or the branch is protected;
- the upstream work tree is dirty or the release tag/assets are missing;
- `versionCode` did not increase;
- the release tag or asset name does not match the reproducible templates;
- the Gradle build requires the release keystore and `-Pfdroid` is not implemented;
- the app is not FOSS, uses non-free dependencies, or the license is unclear;
- `fdroid lint` reports a policy problem that would require hiding files;
- the metadata needs a category that does not exist in the official list;
- a validation loop exceeds five iterations.
